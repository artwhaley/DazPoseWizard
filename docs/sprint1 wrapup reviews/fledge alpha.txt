Bridging hand contact → member (the gap)
Your mental model needs three pieces to become production:

Make the male avatar a real performance fixture. Today PartnerAnatomyTestController is a test menu. Move erection state, centerline guides, and compliance offsets into a runtime component on the Player (PlayerAnatomy / a G8MAnatomy profile), with the same ScriptableObject-profile pattern Performer uses (LaraRightHandGrip.asset-style). The compliance bone offsets should live there too.
Make the member a IGripTarget. The grip stack already accepts IGripTarget.Evaluate(position01). Give the member an analytic contact surface (centerline + radius, mirroring GripContactRod) backed by the erection morph's actual endpoint, not a fixture cylinder. Then succubus.grip(penis) is just another target resolution.
Compliance + motion finishing. "Finishes" for the member: (a) sample the erection morph's endpoints as the member follows subtle hand motion (root tracking with stiffness, not a rigid follow); (b) squeeze — drive a subtle width morph/bone scale from measured grip contact force or digit spread; (c) toy-style commandeered motion — let MotionDriver optionally push the member through a low-amplitude follow channel so the job animates even without full hand animation. Keep one authoritative playback clock (the rule already in your vocab doc).
What to defer: full mesh-vs-skin contact, intermediate-state shell morph correctness, visual finger approval. Those are art-pipeline validation, not authoring blockers.
Wardrobe: the system is wired against itself
The guts are reasonable; the failure you describe is a real bug chain, not a UI problem alone:

Two sources of layer truth. WardrobePreset.Parts returns a deep clone, so artist layer edits in ClothingSetupWindow land in WardrobeConfiguration.assignments but the preset assets keep stale Parts.
Save forks and never writes back. Saving on a released catalog forks into Assets/Wardrobe/Candidates/working-<hash>/, rebinds the current scene, and the canonical WardrobeCatalog.asset never advances. Every other scene and the "default catalog" path stays stale.
Released-catalog gate. ConfigurationApplies() requires configuration.GenerationHash == catalog.ReleasedGenerationId (or the default catalog is a candidate, in which case all outfit commands fail NotReleased). Result: your layer assignment is silently ignored and the old preset.Parts wins — exactly the symptom you described.
UI reality: the Clothing Setup controls exist only in the Unity Editor window; there is zero wardrobe surface in the Avalonia app. Edit-mode toggles go to _session only and can't live-preview (Application.isPlaying gates), so you never see the divergent state until Play Mode.
Suggested workflow, not just a UI pass: make WardrobeConfiguration the single source of truth for layer assignments (presets store only fittings), make WardrobeFitCompiler.Compile a pure function, make SaveConfiguration either mutate the canonical assets or require an explicit Publish step with visible state, and show the candidate/released/fork status prominently in the window. The "one persistent ClothingSetup scene" is right; the asset-state machine around it needs to be obvious.

Gap to the target authoring surface
succubus.dissolvein(startlocation) / say() / tryremoveclothinglayer() / grip(penis) / gripfollowmotiondriver() has no implementation today — no interpreter, no Say verb, no outfit verb in a runnable scene, and grip exists only against analytic rods. The seam is typed C# on SuccubusPerformer (+ ToyControlService under Player.Toys), which is the right shape to script against; what's missing is the thin dispatcher over it and the missing Say/outfit runtimes.
