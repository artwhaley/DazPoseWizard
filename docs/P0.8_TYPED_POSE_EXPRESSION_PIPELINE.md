# P0.8 — Typed Pose/Expression Pipeline + Persistent Expression Runtime

## Baseline

Start from current main. The implementation baseline reviewed when this packet was authored was:

7263902f11ff5c4f2308527275b8eb9a595ac5d3 — Fix head attention and add SALSA dependency

Before implementation, re-read current main and treat newer commits as authoritative. Do not restore older versions of performer files or validation tooling.

P0.8 has two explicit execution stages:

- P0.8A — Typed Pose / Expression import pipeline.
- P0.8B — Persistent runtime Expression state.

Do not blur the stages. P0.8B consumes the production asset proven by P0.8A.

## Current architecture that must remain intact

The current performer graph is conceptually:

PerformerBodyPose
→ base-state capture
→ PerformerBreathing
→ PerformerGaze + PerformerAttentionLife
→ PerformerBlink
→ Animator

The current desktop app has one Unity destination tree, one CanonicalImportRoot, one FinalPoseAssetRoot, and conversion identity is effectively source + destination.

The current Unity browser importer assumes every canonical import produces an AnimationClip plus PerformerPose.asset.

SALSA is present as a dependency, but P0.8 does not integrate speech or lipsync.

## Core product decision

The DAZ library does not need to classify source presets as poses or expressions.

The same DAZ preset may be imported as either product.

The user's drop destination declares intent:

- Drag to UNITY POSES → produce a full PerformerPose product.
- Drag to UNITY EXPRESSIONS → produce a sanitized PerformerExpression product.

Do not add a modal asking Pose vs Expression.
Do not infer product kind from DAZ filename, folder, metadata category, or guessed morph names.

## Non-negotiable compatibility rules

1. Existing Pose import behavior remains production-compatible.
2. Do not move or rename existing Pose assets.
3. Existing configured Pose roots remain valid.
4. Existing schema-1 Pose bridge/status records continue to reconcile as Pose.
5. A source converted as Pose can also be converted independently as Expression.
6. Conversion identity becomes source + kind + destination.
7. Existing P0.4–P0.7 performer behavior and tests remain intact.

## A21. Add PerformerExpression asset

Create PerformerExpression as a ScriptableObject production wrapper analogous to PerformerPose.

- AnimationClip clip

- RendererPath

## A22. Expression clip / wrapper parity

# P0.8B — Persistent runtime Expression state

## B1. Runtime objective

Add persistent semantic facial state:

- Expression(expression)
- Expression(expression, intensity)
- ExpressionAsync(...)
- ClearExpression()

Meaning:

“Maintain this facial Expression until replaced or cleared.”

It is not a one-shot animation, gesture, blink, pose, speech event, or random life behavior.

## B2. Performer graph

Insert Expression after Gaze and before Blink:

PerformerBodyPose
→ base-state capture
→ PerformerBreathing
→ PerformerGaze + PerformerAttentionLife
→ PerformerExpressionLayer
→ PerformerBlink
→ Animator

This ordering is deliberate.

Expression establishes facial state.
Blink closes the remaining eyelid distance over that state.

P0.9 is expected to place speech/visemes conceptually between Expression and Blink. Do not integrate SALSA now.

## B3. Sparse ownership

Runtime Expression may modify only channels listed in PerformerExpression.Channels.

It must not write:

- Transform channels
- breathing-owned channels
- autonomous blink channels
- unrelated blendshapes

## B4. Intensity semantics

Expression intensity is normalized 0..1.

For each Expression-owned channel:

B = incoming base facial value
T = imported Expression target
I = intensity

Settled output:

Lerp(B, T, I)

Therefore:
- I=0 → exact incoming value
- I=1 → full imported target
- partial intensity blends from current incoming face toward target

Do not implement targetWeight * intensity because incoming Pose/future face state may already be nonzero.

## B5. Incoming face remains live

Expression is an overlay, not a permanent snapshot of the incoming face.

If upstream facial value changes while a partially weighted Expression is active, final output must continue to be calculated against the current incoming stream.

This matters when changing full-body Pose while Expression remains active.

## B6. Focused Expression animation job

Use a focused AnimationScriptPlayable / IAnimationJob implementation.

For each resolved Expression channel maintain enough state to represent source and target Expression contribution.

A clean model is:

- source target value + source influence
- target target value + target influence
- transition progress

For incoming B:

sourceOutput = Lerp(B, sourceTarget, sourceInfluence)
targetOutput = Lerp(B, targetTarget, targetInfluence)
final = Lerp(sourceOutput, targetOutput, transitionProgress)

Channels not owned by the current side have influence 0.

Do not build a generic animation-layer registry.

## B7. Transition timing

Add a default Expression blend time to SuccubusPerformer.

Start in the visually reasonable 0.2–0.35 second neighborhood and tune manually.

A simple smooth/ease curve is enough.

No windup or overshoot in P0.8.

## B8. Latest intention wins

No queue.

If Smile is 40% blended in and Smirk is requested, transition from the current evaluated Expression state directly to Smirk.

Do not finish Smile.
Do not return through neutral.

## B9. Exact interruption continuity

When retargeting mid-transition, collapse the currently evaluated Expression contribution into the new source representation rather than sampling the final Blink-composited face.

For a channel at actual transition progress q:

Ws = source influence
Wt = target influence
Ts = source target
Tt = target target

Current effective influence:

W = (1-q)Ws + qWt

If W > epsilon, equivalent current target:

T = ((1-q)WsTs + qWtTt) / W

If W is effectively zero, the channel has no current Expression influence.

Use the actual evaluated transition-curve progress.

This preserves the current output relative to arbitrary incoming base values and avoids retarget pops.

## B10. ClearExpression

ClearExpression means:

“Smoothly remove Expression influence and reveal the current incoming facial state.”

Target all Expression influences toward zero over the configured blend time.

Do not hard-reset blendshapes to zero.
Do not require a Neutral Expression asset.

Clear during an in-progress transition starts from the current evaluated Expression state.

Pending old Expression waiter resolves Superseded.

## B11. Public API

Provide a simple API approximately equivalent to:

- void Expression(PerformerExpression expression)
- void Expression(PerformerExpression expression, float intensity)
- void Expression(PerformerExpression expression, float intensity, float blendTime)
- Awaitable<ExpressionCompletion> ExpressionAsync(...) corresponding overloads
- void ClearExpression()
- void ClearExpression(float blendTime)

Equivalent overload shape is acceptable if cleaner.

## B12. Completion semantics

Add:

ExpressionCompletion:
- Settled
- Superseded
- PerformerDisabled

ExpressionAsync means begin transitioning and resume when that persistent Expression state settles.

The Expression remains active after await completion.

## B13. Same desired state

Expression identity includes:

- asset
- intensity

If same asset/intensity is already transitioning:
- do not restart;
- new async callers join current request.

If already settled:
- ExpressionAsync completes immediately Settled.

Same asset with a different intensity is a new desired state.

## B14. Supersession/reentrancy

New Expression request supersedes pending old request.

Publish the new coherent desired/runtime state before completing old awaiters, preserving the reentrancy discipline already proven by Pose.

## B15. Runtime wrapper validation

On request validate:

- non-null PerformerExpression
- non-null clip
- nonempty channel metadata
- every channel uniquely resolves to a live SkinnedMeshRenderer/blendshape under Lara

Fail clearly for malformed assets. Do not silently play half an Expression.

Resolve/cache bindings outside per-frame animation processing.

## B16. Expression + Blink

Expression may own squint/eye-narrowing morphs but import sanitation excludes autonomous full blink controls.

Expression runs before Blink.

Blink then closes the remaining distance from incoming eyelid state to full closure using its existing composition.

Required visual behavior:

Expression narrows eyes
→ Blink closes fully
→ Blink opens
→ Expression narrowing is visible again

Do not change existing P0.7 Blink semantics.

## B17. Expression + Gaze / Attention Life

Expression must not:
- change gaze target
- change gaze acquisition
- rotate head/eyes
- reseed attention life
- reset eye-fixation/head-bias timers

Expression clips have zero Transform curves by design.

## B18. Expression + Breathing

Expression changes must not reset BreathPhase or own Breathe/BreatheBelly.

## B19. Expression + Pose

Expression persists through Pose changes.

If the new Pose has a different base facial value B, a partial Expression continues to satisfy Lerp(current B, T, I).

ClearExpression reveals the current Pose-authored facial state, not hard zero.

## B20. Base-state isolation

Expression is downstream of PerformerBodyPose base-state capture.

Pose transitions must never capture Expression into their next base source.

Use exaggerated Expression values in acceptance tests to prove this.

## B21. Sparse switching

Test disjoint-channel Expressions.

Example:
- A owns smile
- B owns brow raise

A → B must release smile contribution toward current incoming base while raising brow toward B.

Do not leave A-only channels stuck.
Do not neutralize unrelated channels.

## B24. Disable/re-enable

Pending ExpressionAsync waiter resolves PerformerDisabled before graph teardown.

Preferred persistent behavior:
- remember last desired Expression/intensity;
- restore it snapped/coherently on re-enable;
- never resurrect old awaiters.

Use this behavior unless a concrete technical blocker exists; document any deviation.
