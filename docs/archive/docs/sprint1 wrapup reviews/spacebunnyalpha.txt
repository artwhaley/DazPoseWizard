DazPoseWizard — architecture review before the authoring sprint
The headline
You asked me to find the places where succubus.dosomethingcool will fail because the ability is built on test kludges. The awkward part is that most of the runtime is genuinely good. SuccubusPerformer already exposes DissolveTo, Say, TryRemoveLayer, Grip, Pose, WalkTo, SitAtAsync, Cast — almost exactly the verb set you sketched, with paired Async variants and proper Superseded/PerformerDisabled completion semantics. That layer is not the problem.

The problem is narrower and worse than "missing features": the seams between verbs are named after rig/QA vocabulary instead of body/scene vocabulary. So an authoring script has to know the word "IGripTarget" and hand-assemble a GripContactRod. Every verb is real; the nouns are wrong, and the nouns are the thing you're about to make users type.

1. Test hardware masquerading as production
I ranked these by how badly they'll bite the authoring sprint.

1.1 The grip target is a test fixture — and it's the only one
GripContactRod is the only IGripTarget implementation in the entire codebase, and it says so in its own doc comment:

csharp
Copy
/// <summary>Stable analytic cylinder fixture used by the hand-grip acceptance scene.</summary>
public sealed class GripContactRod : MonoBehaviour, IGripTarget
GripContactRod.cs

Everything downstream is real — GripReachPlanner, PerformerArmIKLayer, PerformerHandGripLayer, 32 bracket steps + 10 binary iterations of collision solve, 20 finger probes. The reach/walk/acquire/active/release state machine in PerformerHandGripController.cs is production-grade. It has never been pointed at an actual body. It has only ever been pointed at a 0.12 m analytic cylinder whose endpoints and normal are hand-placed transforms.

Consequence: grip(penis) doesn't exist, and can't exist without new code. Not "kludgy" — absent.

1.2 The male member is a proof scene, not a character
PartnerAnatomyTestController is the entire state of the member, and it is three separate problems in one 300-line file:

Wrong namespace. It's DazPose.UnityValidation.Partner, sitting under Assets/DazPose/Runtime/. Validation code in the runtime folder, shipped to the player.
Contact data is frozen in root-local space. GetContactFrame returns centerRoot / tangentRoot — pre-baked Vector3[] arrays captured at build time by PartnerRigAcceptanceBuilder.DeriveGeometryLine(...) from two static FBX endpoints, then interpolated by erection01. They're in the character's local frame, so if the member bends, the contact line does not follow the bend. It's a decal, not geometry.
It doesn't implement IGripTarget, and returns Vector3s where the grip system needs a GripFrame (center + tangent + normal + radius).
And compliance — the "squeeze" — is three IMGUI sliders:

csharp
Copy
public void SetShaft1X(float degrees) { shaft1X = Mathf.Clamp(degrees, -5f, 5f); ApplyCompliance(); }
public void SetShaft4X(float degrees) { shaft4X = Mathf.Clamp(degrees, -5f, 5f); ApplyCompliance(); }
public void SetDistributedBend(float degrees) { distributedBend = Mathf.Clamp(degrees, -5f, 5f); ApplyCompliance(); }
PartnerAnatomyTestController.cs

ApplyCompliance writes bone.localRotation directly from LateUpdate. Two consequences worth naming:

There is no input path from the hand. Grip → squeeze does not exist as a signal, at any layer. The user would have to physically drag a slider in the inspector while the grip is active. So: handjob with member movement and squeeze is not "incomplete," it's unwired.
Compliance is gated on Mathf.Approximately(Erection01, 1f) and on (!ShellVisible || ShellFollowsBones). Flaccid members get zero compliance. That's a hard-coded artistic assumption buried in a test controller, and it's the kind of thing that will silently stop working when you swap the mesh.
Also note ApplyCompliance writes bones in LateUpdate while the performer runs an Animation Rigging job graph. The handoff doc already flagged that you specifically avoided "direct LateUpdate skeleton write" for the performer — the member does exactly that. If you ever put the member under the same animator these will fight.

1.3 No assembly boundaries at all
I checked for .asmdef files. There are none except a vendored SimpleJSON. So:

13 harness/selftest/acceptance/fixture classes live in Runtime/ in production namespaces: PerformerPoseAcceptanceHarness, PerformerPoseSmokeHarness, HandGripAcceptanceHarness, HandGripRuntimeSelfTests, WardrobeRuntimeExecutionHarness, WardrobePlayerExecutionFixture, plus six *RuntimeSelfTests and ToyStackAcceptanceSelfTests.
There is no test project. Every "test" is a MonoBehaviour with IMGUI sliders that a human drags, or an editor menu item.
This is why the pattern keeps happening: there's nowhere for test code to go except Runtime/. Fixing the assembly layout is the single highest-leverage cleanup on this list — it's what makes the other kludges stop being able to leak in.

1.4 Production assets point at TestData/
WardrobeCatalog.asset → first-outfit.asset → fit states that live under Assets/TestData/WardrobeRuntime/SetupCandidates/<hash>/. Every outfit mesh, body variant, dissolve profile and surface binding the character wears at runtime is stored in a folder named TestData. Nothing is wrong with it functionally — I verified the GUIDs resolve and the fit states are status: 1 (Validated) with masks 6/2/0 matching the configured layers — but it's a naming lie that will confuse every future agent, including you.

1.5 The toys stack is wired, but by nothing
ToyControlService is a MonoBehaviour that owns ToyMotionFollower instances and takes a serialized _motionDriver. So the chain exists. But there's no verb, no scene wiring, and no ToyMotionBinding authoring path — ToyMotionFollower.cs is internal and constructed only from inside ToyControlService. Your gripfollowmotiondriver() instinct is right; today it's a serialized field you have to remember to fill in by hand, and if it's null the whole toy stack is silently inert.

2. Bridging hand ↔ member
The shape of the fix, at a high level:

Split the member into three responsibilities, and give each one a production type.

Geometry provider. Replace the baked Vector3[] centerline with something that evaluates the actual shaft bones at query time. The bones already exist and already chain correctly — shaft1..shaft7, verified by PartnerRigAcceptanceBuilder. Evaluate tangent from consecutive bone positions, derive the normal from the bone frame, interpolate radius along the chain. That single change kills the "frozen line" problem and makes the contact frame live under bending for free.
Contact surface. Make that provider implement IGripTarget directly, returning a real GripFrame. At that point Grip(partnerMember) works against the real body with zero changes to the planner or the solver — the interface was already designed for it. GripContactRod stays as the null-object for tests and calibration; it just stops being the only citizen.
Compliance. Turn shaft1X / shaft4X / distributedBend from sliders into a driven signal with a sane default. The math already exists and is already validated (ValidateParameterAndComplianceMath() runs in the builder). What's missing is a source: grip pressure / stroke speed / a per-verb authored amount. Give it an input like Squeeze01 on a small runtime component and let the grip controller write it.
Two things to be deliberate about. First, don't put the member's bones under the performer's animator graph — the performer already owns a two-bone IK job plus20 finger writes, and a second writer on the same skeleton is how you get silent one-frame fighting. Keep the member as its own rig with its own small update, as it is now, but get it out of LateUpdate-sliders and behind a real component. Second, the erection morph is currently driven by a Erection01 slider with no arousal source. For a 2-minute authored scene that's arguably fine (the script can set it), but you should decide deliberately whether erection is an authored verb or an emergent product of the toy driver, because it changes what Say() lines get selected.

The naming fix is the actual authoring win. Don't expose IGripTarget to script authors. Expose something like penis / member as a scene-level named anchor, resolved at load. Same for GripContactRod — no author should ever type that word.

3. Wardrobe: your gut is right, and there's a real bug underneath the UI problem
You said assigning items to layers doesn't take effect after a save. I found the bug, and it is not a UI problem. It's a split-brain between two sources of truth, and it's already visible in your committed assets.

The bug
Layers live in two places:

WardrobePreset.Part.layer — baked into the preset asset
WardrobeConfiguration.PieceAssignment.layer — an override table keyed by (presetId, pieceId)
At runtime, PerformerWardrobe.cs prefers the configuration table, but only if ConfigurationApplies():

csharp
Copy
private bool ConfigurationApplies() => configuration != null &&
    (!catalog.IsReleased || allowCandidatePreview || configuration.GenerationHash == catalog.ReleasedGenerationId);
Now look at what SaveConfiguration does:

csharp
Copy
pair.Key.ConfigureGenerated(pair.Key.PresetId, ..., pair.Key.Parts, ...);   // Parts passed through UNCHANGED
...
targetConfig.CommitRevision(generation, new[] { generation });
ClothingSetupWindow.cs

Two failures compound:

Save never bakes your layer choices into the preset. It hands pair.Key.Parts straight back to ConfigureGenerated. The artist's layer assignment only ever lands in WardrobeConfiguration.
In the released-catalog path, Save writes a hash that can never match. generation becomes HashText(_catalog.ReleasedGenerationId + "/" + assignmentHash) — a hash of the released ID — and commits that as configuration.GenerationHash. ConfigurationApplies() compares it for equality against catalog.ReleasedGenerationId. It can never be equal.
So the moment you save layer edits against a released catalog, ConfigurationApplies() goes false, ResolveLayer falls back to preset.Parts[].layer, and the preset still says layer: 0 for everything. The save reports success — "Saved revision N; all outfit masks compiled and validated." — and changes nothing at runtime. Exactly your symptom.

It's already bitten you: WardrobeConfiguration.asset (revision 2) says first-outfit → Panty = layer 2, PeekaBoo = layer 1. first-outfit.asset says layer 0 and layer 0. The fit states were compiled for masks 6/2/0 (correct, config-driven) while the preset lies about being all-base. Right now the unreleased catalog saves you by short-circuiting !catalog.IsReleased to true — so this is a landmine with a countdown, not a live outage.

The publisher does it correctly, incidentally — WardrobeGenerationPublisher.SnapshotPreset bakes part.layer from the assignment map. So the right model already exists in the codebase; the daily Save path just doesn't use it.

Fix: one source of truth. Bake layer assignments into preset.Parts in SaveConfiguration exactly as the publisher does, then treat WardrobeConfiguration as an authoring input rather than a runtime overlay. Delete the generation-hash equality gate — or if you want a drift guard, make it a warning that names the mismatch, never a silent fallback.

The UI, which genuinely is bad
You're right that you can't tell what the controls do. Concretely:

The layer control has three states presented as two. "Layer 1" / "Layer 2" toggles where Base is implied. There is no way to see or set Base directly, and no indication of what Base means for the piece you're looking at. The help text says "Base is always the first layer removed" — which doesn't explain ordering.
Layers are per-piece with no grouping. A real outfit is "underwear / clothing / outerwear." The window shows a flat list of meshes with (role) in parentheses, and role comes from the DAZ source node — an import artifact, not an authoring concept.
Ordering is invisible and nondeterministic. The list order is preset.Parts order, which is DAZ import order. Nothing tells the artist which piece comes off first.
The unsaved state is easy to lose. _session.IsDirty gates the Save button, and OnFocus calls RefreshBinding, which rebuilds the session only when not dirty — so a focused-but-not-dirty window will silently reload and discard. Losing work to a window focus event is the kind of thing that makes people stop trusting a tool.
Opacity is a per-material-slot matrix that has nothing to do with layers, sharing equal visual weight with the layer list. It's authoring materials, not wardrobe.
Save, Revert, Create Variant, and Publish are four buttons in three rows with different enable rules, and the only explanation of why a button is greyed out is a warning box at the bottom.
The fit-state panel is the real feedback loop and it's buried below the fold, after opacity and footwear. It already knows the answer ("Mask 6 · Validated · bent-foot pose"); it should be the primary display.
Workflow I'd rebuild toward: one screen, three columns — what's on the body (stack, top to bottom, drag to reorder, the removal order is literally the visual order), what's available (the catalog), what it compiles to (fit states, live). Show dirty state as a persistent header bar with an explicit "unsaved" count, not as button greying. And make the preview the primary surface — you're already forced into Play Mode to see anything, which is right; the authoring pass should happen there, not in the inspector.

4. Two more things you'll hit in the authoring sprint
There's no line vocabulary. Say(AudioClip) takes a raw clip and PerformerSpeech is an internal queue. Your say(WelcomeClip) example implies content authors pick lines, which means you need a named-line registry mapping ID → clip + lipsync data, and a selection policy. PerformerSalsaLipSync and PerformerLipSyncMorphCatalog exist underneath, but nothing joins a line to its viseme track.

The two-minute scene has no clock. Every verb is fire-and-forget or Awaitable. You need a sequencer with a timeline, cancel-on-supersede, and — critically — a policy for what happens when two verbs want the same body region. Today that arbitration is scattered: grip owns the arm and suppresses motion via MotionSuppression, the expression layer rejects non-head channels on a grip-enabled animator, wardrobe refuses during a dissolve. Those are three bespoke mutexes that don't know about each other.
