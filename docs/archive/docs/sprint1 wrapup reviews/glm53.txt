Bridging handjob ↔ penis: the member as a contact column
The good news is the contract side is already solved. IGripTarget.Evaluate(position01) → GripFrame {Center, Tangent, Normal, Binormal, Radius} is source-neutral, and the hand already tolerates a moving target (per-frame re-evaluation, replan thresholds, walk-reacquire). What's missing:

The column. A production MemberContactTarget : MonoBehaviour, IGripTarget on the male that, every frame: rebuilds the centerline from the live shaft1–7 bone world transforms plus evaluated tip (7 segments is plenty — your own characterization says so), blends flaccid→erect centerlines and radius (2.06 → 2.33 cm nominal) from Erection01, and returns the GripFrame. The donor pelvis must auto-follow the male's animated pelvis every frame — the pattern exists in the test controller's ApplyDonorFollow (capture offset once, re-apply from base each frame) but needs to become a component tied to the real rig, contingent on the donor-pelvis-sync export gate.

Compliance (the member moves a little during the job). Use exactly the pattern the test controller proved: capture erect base rotations once; every frame apply bounded offsets from base (never accumulate). Two drivers: (a) small palm-force reaction — push the affected shaft segment slightly along the grip frame's normal/binormal proportional to finger weight × grip strength × velocity, clamped ±3–5° like the existing shaft1/shaft4 sliders; (b) pJCM_Shaft1_up corrective for base-angle changes, gated on erection state as the characterization doc suggests. Delete the controller's rod special-case in the same pass and replace with a clean "position source drives target evaluation" rule so the fixture stops living in runtime code.

Squeeze. You already have the hand-side scalar: gripStrength01 exists on the profile/controller but isn't exposed on the performer facade. Add Squeeze(float strength)/Grip(target, strength) — it maps to finger curl pressure (already weighted: fingers blend in above 0.7 arm weight) plus member-side response: radial squash via negative Shaft Inflate or Glans Flatten, clamped to source ranges, erection-gated. Parametric and authored first; spring sim later. The hand side needs nothing new — this is mostly exposing an existing field and adding the member's pressure response.

Prereq gates before this is real (from your own characterization): bone-ERC/animation export probe for Flacid, donor pelvis sync verification, the thigh-weight anomaly, the shell-following decision, and a generated G8M PerformerSurfaceBindingAsset so dissolve/particles work on the male. The erection proof gives you centerline/radius data to build against immediately.

Wardrobe: why layer assignments don't stick
The guts are good — PerformerWardrobe.cs is a proper queued, atomic, rollback-capable switcher, and the spec (WardrobeRuntimeAndSetupSpec.md) is genuinely excellent. The failure you're feeling is in the config-identity and window layer:

The silent hash gate. ResolveLayer() only honors saved assignments when ConfigurationApplies(): !catalog.IsReleased || allowCandidatePreview || config.GenerationHash == catalog.ReleasedGenerationId. On a released catalog, SaveConfiguration in ClothingSetupWindow.cs doesn't update the release — it forks a working candidate under Assets/Wardrobe/Candidates/working-* and rebinds with candidatePreview: true (in-window only). If you save and then check the result from any scene whose PerformerWardrobe still references the released catalog, the hash no longer matches, allowCandidatePreview is false, and the runtime silently falls back to the preset's import-time layers. Your reassignments exist in the configuration asset and are ignored without a single warning. The converging path exists (Save → "Publish validated generation" → hashes realign), but nothing in the UI tells you that's mandatory, so it reads as "save does nothing."

Three compounding traps: (a) Save hard-aborts if any preset compiles to Needs Fit, reporting only in a help-box at the bottom of a long scroll; (b) edits in Play Mode are disabled rather than captured; (c) the runtime caches layer/material bindings at init, so a config change mid-Play can't show up anyway — and nothing distinguishes "stale binding" from "applied."

What the controls rebuild should be. Keep the runtime contract exactly as specced (three layers, ceiling semantics, TryRemove/TryAdd, footwear-as-piece — all correct). Rebuild the window around one visible state machine:

A binding provenance bar: which catalog/config the runtime is bound to, released generation vs config revision, and a loud ✗ STALE badge with a one-click "Rebind / Publish" when they diverge. This alone kills the bug you're feeling.
A Draft → Save → Publish wizard instead of three unrelated buttons; Save on a released catalog visibly announces "this creates a working candidate — publish to apply," or better, offers "Save + Publish" as one action.
Piece rows grouped by current layer with layer badges and per-layer counts, role icons (garment/footwear/hair), not two unlabeled toggle-buttons among 40 rows of sliders.
Fit-state table per reachable mask with Needs-Fit items clickable and blocking only the affected preset's publish, not the whole catalog's save.
Editor-session layer: keep WardrobeEditSession, but add real Undo and a dirty-reason list ("what will Save change").
The spec's section 9 (isolation view, pose/morph probes, footwear cm readouts) is the destination; you don't need all of it before the authoring sprint — you need provenance, save/publish clarity, and layer badges.
Also: the validated ClothingSetup scene still lives only in the isolated project (per progress.json: runtime/layers gates incomplete, integration failed, scene "isolated, not published"). Publishing the scene + the save/apply fix are the two user-visible wins; the remaining stress/walk evidence can slip a sprint.
