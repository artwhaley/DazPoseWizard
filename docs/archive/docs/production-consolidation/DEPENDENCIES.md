## Current assembly boundaries

- `validation/DazPoseUnityValidation/Assets` contains one asmdef: vendor `Assets/Daz3D/Vendors/SimpleJSON.asmdef` (assembly `SimpleJSON`, auto-referenced, no explicit references). No asmdef was found for `DazPose`, `Player`, `FirstPerformanceVoid`, or the validation code.
- Consequently, first-party scripts outside special `Editor` directories compile into Unity's predefined `Assembly-CSharp`; scripts under `Assets/Editor` and directories named `Editor` compile into `Assembly-CSharp-Editor`. The directory split is currently the principal runtime/editor boundary, not assembly definitions.
- Runtime folders contain both production components and validation/acceptance components (for example `PerformerPoseSmokeHarness`, `WardrobeRuntimeExecutionHarness`, and toy self-tests). Some runtime files wrap editor-only references or helper methods in `#if UNITY_EDITOR`; this keeps those portions out of a player but does not exclude the component/class itself. `WardrobeRuntimeExecutionHarness` has editor-only setup/report paths behind `UNITY_EDITOR`, while player report code is intentionally usable by the validation player. `PerformerSalsaLipSync.SetEditorReferences` is also editor guarded.
- Many authoring/import/baking/validation entry points live under editor directories, including Clothing Setup, wardrobe builders and validators, First Performance Void setup, import processors, animation baker tools, and grip setup/report tools. Those code paths can access `UnityEditor` and editor-only HDRP APIs by virtue of their folder placement.

## Existing Clothing Setup persistence runner and proposed diagnostic

Existing entry points are `scripts/run-wardrobe-execution.ps1` stages `Setup` and `Persistence`, dispatching to `WardrobeExecutionValidation.Setup()` and `.Persistence()` in the isolated copy. `Setup()` opens/builds the persistent Clothing Setup scene, checks the candidate catalog/configuration binding, exercises `WardrobeEditSession` layer editing/revert, and requires fresh Runtime evidence. `Persistence()` creates disposable cloned configuration/catalog assets, mutates the edit session, explicitly saves/reloads assets, checks release snapshots/failures, and removes its temporary assets in `finally`. These stages are batch-friendly and safer than operating on the user's source catalog.

Neither stage invokes the actual private `ClothingSetupWindow.SaveConfiguration()` method. That handler has consequential editor behavior: it compiles all target presets, mutates configuration and presets, calls `AssetDatabase.SaveAssets()`, may fork a released catalog and rebind/dirty/save the setup scene, marks the session committed, and refreshes the window. Passing the current Persistence stage therefore does not establish that the real window Save path works.

Diagnostic design used by the supervisor (independent of the blocked suite):

1. Work only in the already isolated validation project after verifying no Unity process owns it; do not run the window handler against the main project. Use an isolated disposable scene/catalog/configuration and canonical body renderer already staged there.
2. Add a narrowly scoped Editor diagnostic entry point (or temporary local-only harness) that instantiates `ClothingSetupWindow`, binds cloned catalog/config/body/wardrobe and a `WardrobeEditSession`, changes one valid piece layer, then invokes the same `SaveConfiguration()` method used by the button. A small internal method/refactor seam is preferable to reflection, but avoid changing production assets or acceptance policy merely for the probe.
3. Capture before/after configuration revision and assignment, preset `ConfigurationRevision`/fit-state snapshots, catalog release state and generation, scene binding, handler message, plus relevant hashes. Assert successful save advances the clone's revision and persists/reloads the selected layer and compiled fit states. Separately run a known invalid candidate through the same handler to confirm it reports failure without partial writes. Keep any generated assets beneath an isolated disposable root and clean them in `finally`.
4. If a full persistent asset/scene Save test is required, use a disposable copy of the setup scene and cloned ScriptableObjects in the isolated project; do not save the checked-in setup scene or source assets. Compare scene/catalog/config file hashes before and after cleanup, and preserve the report/log under ignored `TestOutput`.

The supervisor used local-only reflection helpers in the disposable project, retained the generated evidence and did not copy mutations back. Actual outcomes are in `BASELINE.md`; this design description is not itself test evidence. Day 5 should make the operation return a structured result rather than parsing a UI message.

## Day 6 risks

2. Runtime-to-editor reachability needs particular care around mixed validation components and editor guards in runtime folders, including HDRP-bearing harnesses and self-tests.
3. SALSA is a precompiled runtime DLL with separate editor tooling; Buttplug is a local precompiled package DLL. Preserve effective plugin availability through automatic or explicit assembly references and verify Windows runtime closure after extraction. Current predefined-assembly packaging succeeds, which is useful evidence but does not certify future asmdefs or physical hardware.
