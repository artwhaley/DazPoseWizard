# Production consolidation reproduction helpers

These sources stay outside Unity's Assets directory. They are validation observers, not a production dependency. Runtime/prefab composition does not call them.

Use only `.dazposewizard/production-consolidation`, with a fresh copy of the current main Assets/Packages/ProjectSettings and the new production assets. Never copy an earlier diagnostic project's changed drafts or acceptance scenes into main. Keep one Unity process per project. `Day2Validation.Run` and `Day2Build.Run` enforce the disposable path; targeted preflight/dependency templates additionally enforce batch mode. An extra staging guard in these templates does not change their tested observations.

Copy `Day2Probe.cs` into the disposable project's `Assets` directory, and the other four `.cs` files into its `Assets/Editor` directory. Run Unity batch mode with `-executeMethod Day2Validation.Run` without `-quit` or `-nographics`: the validator enters/exits Play Mode and owns completion. It generates its technical expression/probe scene inside the disposable project, records `TestOutput/day2/runtime.json` and `validation.json`, and exits. This test deliberately exercises saved defaults and Undo, so keep its scene changes in staging.

`Day2Preflight.Run` checks the additional capability failures and invokes `Day2Build.Run` on success. Build uses the generated `Assets/TestData/ProductionValidation/Day2Probe.unity` scene, Development/Windows x64, and writes `TestOutput/day2/build.json` and `player/Day2Probe.exe`. The player writes `day2-player.json` beside the executable. Run with graphics; Null graphics cannot establish effect behavior. The player never issues device commands. A non-batch launch holds its final view for 20 seconds before closing.

`Day2Dependencies.Run` records the prefab/scene dependency paths. Compare asset bytes with PowerShell `Get-FileHash`; Unity Mono file streams rejected some long generated Windows paths. Package paths are resolved from the unchanged manifest/lock file.

The actual executed helper revisions, logs and hashes remain in `.dazposewizard/day2-evidence/` and the disposable project's `Assets`. The one-time intermediate prefab-root conversion helper is evidence only and is unnecessary for reproduction: the exported prefab and production builder now put the performer on the root. See [DAY_2_REPORT.md](../DAY_2_REPORT.md) for acceptance evidence and manual checks.

Environment authority: ProductionTestEnvironmentBuilder.Compose uses the saved Assets/Scenes/FirstPerformanceVoid.unity scene, preserving its authored environment and camera. Use it before generating probe scenes if rebuilding the test composition. Never run FirstPerformanceVoidBuilder to recreate this environment from defaults.

VoidCorrection.Run verifies authored environment/light preservation and invokes Day2Validation.Run. VoidBuild.Run records dependency paths and invokes Day2Preflight.Run plus its build. These helpers operate only in disposable staging. The environment correction report is the current composition evidence.

Day 3 helpers: copy Day3SceneBuilder.cs, Day3Validation.cs, Day3Build.cs and Day3Dependencies.cs into the disposable project's Assets/Editor. They require the exported Day 2 composition and current product code. Day3SceneBuilder.Create creates/saves the runner and fixture references, then invokes Day3Validation.Run. Day3Validation.Run opens the already saved scene and never injects components; run without -quit/-nographics because it enters Play Mode and exits on completion. Day3Build.Run builds only Assets/Production/Scenes/Day3CommandValidation.unity. Day3Dependencies.Run inventories that scene. Helpers are evidence/reproduction tools and must stay outside the main project's Assets.

The shipped Day3RegressionRunner is product-project validation code and already lives in the saved scene. No helper is needed for pressing Play. See ../DAY_3_REPORT.md and ../DAY_3_MANUAL_CHECKS.md. Test hardware uses a fake backend; physical behavior remains separate. The final facade file preserves its original CRLF style; canonical source comparison ignores line terminators only, and Git whitespace checking uses core.whitespace=cr-at-eol.

Day 5 helpers: copy `Day5*.cs` into the disposable project's `Assets/Editor`. `Day5PrepareSetup.Run` composes the persistent Clothing Setup scene from the accepted Day 2 Void data, binds the global saved candidate, records prefab overrides and compiles it. `Day5SceneBuilder.Create` creates a separate edited candidate/release comparison fixture and saves its runner. Do not recreate an existing immutable generation on a validation rerun: use `Day5Validation.Run` against the saved scene. `Day5RepairSceneBinding.Run` is the one-time repair for the first fixture's missing prefab property overrides; it records that binding without republishing.

`Day5Validation.Run` executes the exact saved wardrobe scene, then the exact saved Clothing Setup scene, and `Day5Build.Run` builds each separately. Run graphics-enabled without `-quit`/`-nographics`. Their runners live in the scenes: `Day5WardrobeRunner` and `ClothingSetupPreviewRunner`. The latter opens a visible, dressed preview for normal Play and exercises removal/restoration only in batch validation. No injection is needed for manual Play.

`DazPose.UnityValidation.Day5WardrobeValidation.RunBatch` runs transactional and actual setup-handler regressions with copied real source packages. It writes `TestOutput/day5/transactions.json` and owns process exit. Source file hashes and package dependency identities are recorded in the report. Contract/Migration entry points additionally require `-wardrobeExecutionStage`, `-wardrobeExecutionReport`, `-wardrobeExecutionSourceHash` and `-wardrobeExecutionInputHash` arguments.

After editor and Windows player checks pass, `python export_day5.py` exports only the two saved scene dependency closures. It refuses unexpected overwrites or concurrent edits to authorized baseline assets, backs up repaired assets, preserves original GUIDs, and checks imported sources plus protected scenes/prefab. `python day5_evidence.py` records complete first-party source/meta parity, exact YAML environment comparisons and an evidence ledger. These Python helpers resolve the repository from their own location; they are not runtime dependencies.
