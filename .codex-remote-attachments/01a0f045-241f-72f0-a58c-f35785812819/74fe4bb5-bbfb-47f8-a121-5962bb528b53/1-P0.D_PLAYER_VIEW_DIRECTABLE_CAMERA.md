## 1. Goal

Create the first real **Player** runtime object and turn the current scene camera into a directable, polished first-person viewpoint.

The camera is not debug machinery. It is the player's portal into the world and will shortly be one of the primary tools used to author the first 30-second directed performance.

The player currently needs to own only:

- world viewpoint position
- directed head / view orientation
- `MainCamera`
- `AudioListener`

In the future Player may also own a visible player model, input, interactions, XR tracking, and other player state. **Do not implement those future systems now.** Build only the smallest architecture that gives them a clean future home.

## 3. Player Hierarchy

Convert the camera area into this hierarchy:

```text
Player
└── ViewRig
    └── HeadPose
        └── MainCamera
```

Attach `PlayerController` to `Player`.

Attach `PlayerView` either to `Player` or `ViewRig`, whichever produces the cleanest implementation.

Preferred conceptual ownership:

```text
Player
    owns world-space player/head position

ViewRig
    owns game/director-controlled view orientation

HeadPose
    reserved for future LOCAL head/XR tracking

MainCamera
    actual rendered camera
```

For desktop now:

```text
HeadPose.localPosition = Vector3.zero
HeadPose.localRotation = Quaternion.identity

MainCamera.localPosition = Vector3.zero
MainCamera.localRotation = Quaternion.identity
```

The existing camera world pose must remain visually identical after migration.

A simple migration shape is:

```text
Player.position = old MainCamera world position
Player.rotation = identity

ViewRig.localPosition = zero
ViewRig.localRotation = old MainCamera world rotation

HeadPose = local identity
MainCamera = local identity
```

Do not assume this exact transform decomposition if another equivalent decomposition better preserves scene data, but maintain the architectural boundary:

```text
position channel     !=     directed orientation channel
directed orientation !=     future tracked HeadPose
```

## 4. Why HeadPose Exists Now

Do not eliminate `HeadPose` because it is identity today. It is the seam for future XR.

The intended later shape is:

```text
Player
    world/player position
        ↓
ViewRig
    game/director orientation baseline
        ↓
HeadPose
    local OpenXR/HMD movement
        ↓
MainCamera
```

Current `PlayerView` code must **never animate `HeadPose` directly**.

It may animate `Player` world position and `ViewRig` orientation. It must leave `HeadPose` local pose alone.

This means future VR work can add tracked head movement without rewriting every camera choreography command.

**Do not implement XR now.**


`PlayerController` may simply delegate to `PlayerView`. That is acceptable and desirable.

Do not add player input, inventory, interaction framework, model handling, avatar locomotion, event bus, or service locator yet.

## 6. Position and Orientation Are Independent Channels

This is a critical requirement.

**POSITION commands:** `MoveTo(...)`

**ORIENTATION commands:** `LookAt(...)`, `Track(...)`, `StopTracking()`

must operate independently.

Example:

```csharp
player.MoveTo(closeShot, 4f);
player.Track(laraFace, 1f);
```

must mean:

```text
camera position moves for four seconds
WHILE
view orientation tracks Lara
```

Neither command cancels the other.

Latest **POSITION** command wins over prior position commands. Latest **ORIENTATION** command wins over prior orientation commands.

Do not create one giant camera-state transition that makes these mutually exclusive.

---

## 7. MoveTo Semantics

Primary authoring form:

```csharp
player.MoveTo(cameraMark, 3f);
```

This means:

- move Player's world position
- from its current position
- to `cameraMark.position`
- over exactly 3 gameplay seconds
- using the standard smooth ease-in/ease-out

**IMPORTANT:** `MoveTo(Transform)` uses `target.position` only. It does **not** adopt `target.rotation`.

Orientation is a separate explicit channel. This distinction is intentional.

## 9. Float Duration Overload — Important

The normal authoring API is:

```csharp
player.MoveTo(mark, 3f);
```

not:

```csharp
player.MoveTo(mark, someNamedSlowTransition);
```

Passing a float means:

```text
duration in seconds
+
standard smooth ease-in/ease-out
```

The float overload should internally be equivalent to something like:

```csharp
MoveTo(target, ViewTransition.EaseInOut(duration));
```

Do the same for `LookAt` and Track acquisition.

The user should not need to manually construct a `ViewTransition` for ordinary camera direction.

## 11. Exact Movement Timing

Camera position movement must have deterministic duration.

Use:

```text
capture start position
elapsed = 0
normalized = elapsed / duration
eased = transition curve(normalized)
position = Lerp(start, destination, eased)
```

Do **not** use:

```csharp
position = Lerp(position, target, deltaTime * speed);
```

Do not use an asymptotic "eventually gets there" movement.

At the end, set `Player.position` to the exact requested destination within normal float precision.

---

## 12. LookAt Semantics

`LookAt` means:

```text
smoothly turn toward a target
during a finite transition
then STOP updating orientation
```

Example:

```csharp
await player.LookAtAsync(laraFace, 1.25f);
```

means:

```text
over 1.25 seconds:
    turn smoothly toward Lara's current face position

at completion:
    set final exact look direction based on Lara's position at that moment

afterward:
    HOLD that orientation
```

If Lara walks away afterward, the player's view does **not** follow her.

That is the difference between `LookAt` and `Track`.

---

## 13. LookAt Target Behavior During Transition

For `LookAt(Transform target)`, the target remains **live while the finite transition is occurring**.

Each frame during the transition, calculate desired look orientation from the current actual viewpoint position to `target.position` at that frame.

This matters if Lara is moving and the player is also `MoveTo`-ing simultaneously.

At transition completion:

- resolve one final exact desired look orientation
- apply it
- release the target
- hold the resulting orientation

Do not snapshot `target.position` at LookAt command start.

---

## 17. Look Rotation

Use a world-up camera orientation.

Conceptually:

```text
direction = targetPosition - actualViewpointPosition
desired = Quaternion.LookRotation(direction.normalized, Vector3.up)
```

This should produce yaw and pitch with no arbitrary roll.

If direction is effectively zero length, retain current orientation. Do not generate invalid `LookRotation` calls.

---

## 18. Look Transition Interpolation

Like position, finite view transitions must have a known exact duration.

Capture starting `ViewRig` world rotation.

During transition:

```text
desiredNow = current target direction
eased = transition curve(elapsed / duration)
ViewRig world rotation = Quaternion.Slerp(startRotation, desiredNow, eased)
```

At completion:

- recompute desiredNow once
- assign it exactly
- stop the finite transition

This gives us finite authored timing while still allowing the target and/or camera position to move during the look.

---

## 19. Track Semantics

`Track` is persistent orientation behavior.

Example:

```csharp
player.Track(laraFace, 1f);
```

means:

```text
smoothly acquire Lara over one second
then continuously keep the player's directed view following Lara
until explicitly replaced/stopped
```

`Track` does not affect player position. It persists indefinitely.

## 23. Track Acquisition

During Track acquisition:

- capture starting `ViewRig` rotation
- target remains live
- actual viewpoint position remains live
- use standard finite ease-in/ease-out

For the full acquisition duration, do not hard-lock orientation.

At acquisition completion, align exactly toward target's current position, then enter persistent tracking.

---

## 24. Continuous Tracking

Persistent tracking should **not** behave like a perfectly rigid surveillance turret.

Use smooth, framerate-independent angular following.

A reasonable implementation is exponential quaternion smoothing:

```text
desired = LookRotation(target - viewPosition)
alpha = 1 - exp(-deltaTime / responseSeconds)
rotation = Slerp(currentRotation, desired, alpha)
```

Exact formulation may vary if a better mathematically stable equivalent is used.

Requirements:

- frame-rate independent
- no overshoot
- no oscillation
- no hard snap each frame
- modest natural-feeling angular lag

Do not use `deltaTime * arbitrary speed` without making response behavior frame-rate stable.

## 26. StopTracking

Implement:

```csharp
public void StopTracking();
```

Semantics:

```text
if currently persistently tracking:
    stop recalculating orientation immediately

if currently acquiring a Track target:
    cancel acquisition immediately

preserve EXACT current ViewRig orientation
```

Do **not** return to a default direction, original camera rotation, world forward, or recenter.

`StopTracking` means: **hold exactly where my head is currently pointed.**

## 27. Orientation Latest-Wins Policy

Orientation commands form one latest-wins channel.

```text
LookAt(A)
LookAt(B)

A -> Superseded
B begins smoothly from current orientation
```

```text
Track(A)
LookAt(B)

Track(A) ends immediately
LookAt(B) becomes current orientation intent
```

```text
LookAt(A)
Track(B)

LookAt(A) async waiter -> Superseded
Track(B) begins acquisition from current orientation
```

```text
Track(A)
Track(B)

tracking target changes to B
acquire B from the current orientation
```

Do not queue orientation commands FIFO.

---

## 28. Position Latest-Wins Policy

Position is independently latest-wins.

Example:

```csharp
var a = player.MoveToAsync(markA, 4f);
var b = player.MoveToAsync(markB, 2f);
```

Result:

```text
A -> Superseded
B captures current Player position
B moves from there to B over 2 seconds
```

Do not snap to A, return to start, or queue A then B.

---

## 31. Standard Ease

The standard float-overload easing must be explicitly defined by our code.

Use a clean smooth ease-in/ease-out curve equivalent to:

```text
starts velocity near zero
accelerates smoothly
fastest near the midpoint
decelerates smoothly
ends velocity near zero
```

Smoothstep-style behavior is appropriate.

No overshoot, windup, elastic behavior, or bounce.

---

## 32. Custom Curve Safety

For custom `ViewTransition` curves, normalized input is 0..1.

Prefer clamping evaluated transition weight to 0..1 for P0.D.

Camera overshoot is intentionally **not** part of this first implementation.

## 34. Player View Completion

Use one compact completion enum:

```csharp

{
    Completed,
    Superseded,
    PlayerDisabled,
    TargetLost
}
```

`LookAt(Transform)` may additionally use `TargetLost` if its live target disappears during the transition.

---

## 35. Target Loss

For finite `LookAt(Transform)`, if the target becomes null/destroyed before completion:

- freeze current view orientation
- clear orientation transition
- complete waiter as `TargetLost`

Do not throw every frame.

For persistent `Track`, if target becomes null/destroyed:

- stop tracking
- hold current orientation
- emit one useful diagnostic warning

There is no Track waiter to complete.

---

## 36. Reentrancy

Unity Awaitables may resume callers inline.

Before completing an old waiter:

- publish the new active state
- capture current start state
- assign new destination/target
- establish new transition generation

Then complete the superseded waiter.

A continuation from the superseded operation must not accidentally erase the new request.

---

## 37. Disable / Destroy

If `PlayerController` / `PlayerView` is disabled or destroyed, active finite `MoveToAsync` / `LookAtAsync` requests complete as `PlayerDisabled`.

Clear active movement, finite look, and tracking target.

Do not resume half-completed camera direction after re-enable.

On re-enable, preserve the current transform and accept new commands normally.

## 62. Transition Implementation — Position

Store approximately:

```text
start position
target position
elapsed
ViewTransition
async waiters/generation
```

Each `LateUpdate`:

```text
elapsed += Time.deltaTime

t = duration <= 0 ? 1 : clamp01(elapsed / duration)
eased = curve(t)
Player.position = Vector3.Lerp(start, target, eased)
```

At completion, set exact target, publish idle state, then complete waiter as `Completed`.

---

## 63. Transition Implementation — Finite Look

Store approximately:

```text
start ViewRig rotation
target Transform OR fixed target Vector3
elapsed
ViewTransition
```

Each `LateUpdate`, compute current desired orientation and Slerp from captured start rotation using eased normalized time.

At completion, recompute desired orientation, assign exact final orientation, clear live target, hold view, publish idle state, then complete waiter.

---

## 64. Transition Implementation — Track Acquire

Store target Transform, starting ViewRig rotation, acquire elapsed, and `ViewTrackingSettings`.

During acquisition, target and viewpoint remain live. Use finite ease-in/ease-out from captured start rotation.

At completion, apply exact desired orientation and then enter persistent Track state.

Do not let the first persistent Track frame cause a visible snap.

---

## 65. Tracking After Acquire

Each `LateUpdate` while tracking:

```text
if target lost:
    stop tracking and hold
else:
    compute desired current look orientation
    smoothly follow using responseSeconds
```

Persistent tracking is a response system, not repeated finite `LookAt` calls.
